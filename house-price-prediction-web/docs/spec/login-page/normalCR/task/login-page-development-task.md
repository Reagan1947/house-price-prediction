# Login 页面开发任务文档（normalCR）

## 1. 任务目标

依据详细设计文档完成 Login 页面开发，确保实现以下目标：

- 页面视觉与 Figma 保持一致（左侧视觉区 + 右侧登录区）。
- 登录交互满足需求（邮箱校验、密码必填、密码显隐、登录提交）。
- 已登录用户访问 `/login` 时自动跳转 Portal。
- 页面满足基础响应式与可访问性要求。
- 代码符合当前工程规范并通过 lint。

关联文档：

- 需求：`docs/spec/login-page/normalCR/requirements/login-page-requirements`
- 详细设计：`docs/spec/login-page/normalCR/detail-design/login-page-detail-design.md`

## 2. 范围与边界

### 2.1 In Scope

- Login 页面开发（建议 `app/login/page.tsx`）。
- Login 相关组件拆分（`app/components/login/`）。
- Login 页面样式与 token 落地（`app/globals.css` 或局部样式文件）。
- 表单校验与交互状态实现（邮箱格式、密码必填、显隐切换、错误提示）。
- 已登录态路由守卫与 Portal 跳转。

### 2.2 Out of Scope

- 登录后 Portal 页业务开发。
- 鉴权后端接口与数据库实现。
- 忘记密码、注册、多因子认证、SSO。
- 多语言和主题系统改造。

## 3. 任务分解（WBS）

## 3.1 T0 - 开发准备与参数冻结

- 目标：统一输入参数与接口假设，消除实施阻塞。
- 子任务：
  - 确认最终文案（Hero 文案、标题文案、错误提示文案）。
  - 确认 Portal 路径（默认 `/portal`）与登录态判定来源（cookie/session/token）。
  - 确认登录接口契约（请求字段、响应结构、错误码）。
- 产出：
  - 参数确认记录（建议落 PR 描述或 change-log）。
- 验收标准：
  - 无关键未决项后进入开发。

## 3.2 T1 - 页面骨架与路由守卫

- 目标：完成 Login 页面基础骨架与已登录跳转链路。
- 子任务：
  - 新增/完善 `app/login/page.tsx`。
  - 实现服务端优先的登录态检查。
  - 已登录时执行 `redirect('/portal')`（或配置化路径）。
  - 未登录时渲染 Login 页面主结构。
- 产出：
  - 路由可访问，守卫行为可验证。
- 验收标准：
  - 已登录用户无法停留在 `/login` 页面。

## 3.3 T2 - 组件拆分与职责落地

- 目标：按详细设计完成可维护组件拆分。
- 子任务：
  - 新增 `app/components/login/login-layout.tsx`。
  - 新增 `app/components/login/login-form.tsx`。
  - 新增 `app/components/login/email-field.tsx`。
  - 新增 `app/components/login/password-field.tsx`。
  - 在 `app/login/page.tsx` 完成组装。
- 产出：
  - 组件结构清晰，逻辑职责单一。
- 验收标准：
  - 无明显重复代码，组件命名符合项目习惯。

## 3.4 T3 - 视觉样式实现（桌面优先）

- 目标：实现与 Figma 对齐的核心视觉。
- 子任务：
  - 落地双栏布局（左侧背景图/Logo/Hero，右侧表单区）。
  - 实现输入框、图标区、按钮样式（0 圆角、1px 边框、主色蓝）。
  - 对齐关键尺寸（表单宽、控件高度、标题层级）。
- 产出：
  - 桌面端视觉可对照 Figma 验收。
- 验收标准：
  - Header/表单/按钮/文案区关键视觉一致。

## 3.5 T4 - 表单交互与前端校验

- 目标：完成登录表单核心交互逻辑。
- 子任务：
  - 邮箱格式校验（`type=email` + 正则/校验器）。
  - 邮箱非法时展示指定错误提示文案。
  - 密码为空时禁用 `Sign In` 按钮。
  - 眼睛图标实现密码显隐切换。
  - 提交态控制：防重复提交、loading 状态。
- 产出：
  - 表单交互闭环。
- 验收标准：
  - 需求定义的 4 个关键场景全部通过。

## 3.6 T5 - 登录提交集成与异常处理

- 目标：完成提交动作与错误处理机制。
- 子任务：
  - 对接登录 API（或 mock 服务）。
  - 处理成功跳转与失败提示。
  - 区分网络异常、认证失败、服务端异常展示。
- 产出：
  - 可联调的登录提交流程。
- 验收标准：
  - 失败有可理解提示，成功可跳转 Portal。

## 3.7 T6 - 响应式适配（sm/md/lg）

- 目标：保障多端可用与布局稳定。
- 子任务：
  - `lg`：保留双栏 Figma 布局。
  - `md`：压缩比例与表单宽度，保持可读性。
  - `sm`：切换单栏布局（隐藏/弱化左视觉区），确保表单优先。
- 产出：
  - 三断点适配完成。
- 验收标准：
  - 375 / 768 / 1280 宽度无错位、遮挡、横向滚动。

## 3.8 T7 - 可访问性与安全基线

- 目标：满足登录页 WCAG 与基础安全要求。
- 子任务：
  - 补齐 `label`、`aria-invalid`、`aria-describedby`、错误 `role=alert`。
  - 验证 Tab 顺序与 `focus-visible` 可见性。
  - 确保触控区域 >= 44x44。
  - 校验不泄露密码（URL/日志/本地存储）。
- 产出：
  - A11y 与安全基线达标。
- 验收标准：
  - 键盘完整可用，错误可感知，敏感信息不外泄。

## 3.9 T8 - 质量验证与交付

- 目标：完成验收前自测与交付说明。
- 子任务：
  - 执行 `npm run lint`。
  - 执行手工测试（断点、交互、登录态守卫、错误场景）。
  - 输出交付记录与已知限制。
- 产出：
  - 可合并代码与验收记录。
- 验收标准：
  - lint 通过；测试项全部通过或有明确例外说明。

## 4. 里程碑与执行顺序

1. M1：完成 T0（冻结参数与接口假设）
2. M2：完成 T1 + T2（骨架、守卫、组件拆分）
3. M3：完成 T3 + T4（视觉与核心交互）
4. M4：完成 T5 + T6（提交联调与响应式）
5. M5：完成 T7 + T8（A11y/安全验证与交付）

## 5. 任务依赖关系

- T1 依赖 T0（登录态来源、Portal 路径需明确）。
- T2 与 T3 可并行，但需统一样式 token 命名。
- T4 依赖 T2（字段组件已拆分）与 T3（控件样式可用）。
- T5 依赖 T4（本地校验逻辑已稳定）。
- T7 依赖 T3/T4/T6 完成后统一检查。
- T8 依赖全部开发任务完成。

## 6. Definition of Done（DoD）

- 功能：
  - 邮箱校验、密码必填禁用、密码显隐、登录提交、已登录跳转全部符合需求。
- 视觉：
  - 桌面端关键区域与 Figma 一致，移动端无明显视觉回退。
- 工程：
  - 组件职责清晰、命名规范、无重复逻辑、`npm run lint` 通过。
- 可访问性：
  - 语义结构、焦点可见、键盘可达、错误可感知、触控尺寸达标。
- 安全：
  - 敏感信息不落地、不泄露，异常处理可控。

## 7. 风险与应对

1. 文案冲突风险（需求 vs Figma）
   - 应对：以需求文档为主，冲突项在 T0 冻结。
2. 登录态来源不统一（session/cookie/token）
   - 应对：在 T0 明确守卫策略，必要时先实现适配层。
3. 登录接口契约变更风险
   - 应对：使用类型定义 + mock，降低前后端耦合。
4. 移动端视觉压缩导致可读性下降
   - 应对：sm 断点以表单可用性优先，必要时隐藏左侧视觉区。
